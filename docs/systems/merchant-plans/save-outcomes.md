# Issue1373 next prerequisite: correlate asynchronous save outcomes

Draft source plan. Do not implement until pending-identity PR70 merges after required current-head CI. No terminal completion or operational step is included.

Current AsyncSaveStorage worker puts successful callbacks and exceptions in separate queues. WorldState receives UpsertFailedException without the originating callback context, discards its available snapshots and looks up current forms by descriptor. A failed deletion can disappear; a restored replacement can be re-saved as if it originated the failed write. Global errors and delayed callbacks also cannot prove which submission owns a busy flag. The contract must carry job ownership through failure instead of inferring it from a descriptor.

Split into two dependent source PRs on the same issue:

1. Native storage outcome prerequisite, leaving existing callers unchanged. Add a defaultfalse, static SupportsUpsertOutcomes observation to ISaveStorage and a separate UpsertWithOutcome method with a callback taking std::exception_ptr: null means the database call returned, non-null means failure. Default implementation refuses unsupported use; no silent bridge that can lose failures. AsyncSaveStorage opts in and associates the outcome callback with that exact worker task. Submission failure must leave no queued/executing job and no future outcome for that invocation; acceptance has a final nonthrowing publication boundary. Callbacks run only on the owner thread, possibly inline. Keep legacy Upsert callback/error behavior for legacy callers. Queue each tracked task's single tagged outcome for owner-thread delivery, with error and callback captures kept through their destruction. Failed outcomes never increment the finished-upsert count. Success callbacks that throw preserve existing counter behavior. Include new queued, detached, prepared and executing outcomes in IsSettled and retain sticky failure. Database errors and recycling failures cannot queue both success and failure for one task; any failure before outcome publication clears success and produces one failure outcome. Unexpected escaping worker-entry/allocation failures remain fatal, not falsely settled. No new durable-upsert capability is asserted.

2. WorldState adoption and exact retry ownership. Require correlated outcome support before accepting a backend for world saves; update the three in-repo controlled world-storage fixtures to implement the contract. Prepare a shared per-attempt object containing an exact backup of submitted rows, their original weak-instance bindings and all acknowledgement metadata before clearing pending/retry. Keep that backup independently of the vector consumed by storage. Publish the current attempt before calling storage. The outcome callback holds this exact shared attempt and a weak Impl binding, not a raw WorldState or a strong Impl/storage cycle; if the world is destroyed, it cannot mutate freed state. While the submission call is active, stage inline outcomes without acknowledging, releasing the backup or recovering. Only after the call returns successfully may a staged success finalize or staged failure recover. A synchronous throw overrides any staged outcome and recovers once, with no acknowledgement. Track explicit idempotent retirement/recovery so inline failure followed by throw cannot swap an emptied backup over retained retry rows. Only that current attempt may clear busy or acknowledge receipts/transfers. An old or duplicate callback cannot affect a newer attempt. On failure, latch the lifetime flag, retain exact original snapshots in retry using no-throw swaps, preserve callback-queued newer pending keys, and do not reconstruct from live or replacement forms. Returned affected rows are not needed when the exact original batch is still owned. Clear accepted backup only after a valid success acknowledgement completes; callback/preparation failures retain failure and exact recovery state. Synchronous exceptions use the same attempt recovery, even if storage consumed its argument. Refused/unsupported calls do not erase original queues. The old uncorrelated typed error handler must fail closed without guessing current ownership; it is never a recovery source for adopted tracked jobs.
