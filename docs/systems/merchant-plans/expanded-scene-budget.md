## Contract for the first implementation

PR2744 implements game/scene-reward-budget.js as a pure projection over one new, explicitly owned accounting subrecord. The future controller must keep this subrecord, original accepted quest terms and progress in the same actor property and native CAS as any inventory reward. This helper neither writes nor allocates gold; it returns a proposed state and exact reserved reward. It cannot authorize a quest, verify progress, establish ownership, replace session/native fences or create an account cap. Do not import it into the production bundle in this slice.

The record is {v:1,clock,serial,held,paid}. clock is a positive safe-integer server millisecond timestamp. serial is a nonnegative safe-integer reservation counter, never reset when held becomes empty. held maps at most three canonical new quest IDs, each at most48 ASCII characters, to {gold,at,token}. Each gold is an integer10 through150. at is a positive safe-integer timestamp no greater than clock. token is a unique positive safe integer no greater than serial. paid is an ordered array of at most15 [timestamp,gold] pairs with valid timestamps no greater than clock and integer gold10 through150. Unknown version/keys, inherited fields, getters, symbols, sparse/extra array fields and malformed values refuse without mutation or coercion. Native JSON records are the intended caller input, not arbitrary proxies.

Missing accounting state means a new empty budget; present null or malformed state refuses. At every operation require a positive safe integer now at least clock. Validate saved accounting consistency at saved clock before applying any expiry, so a corrupt over-budget record cannot become valid merely by waiting. At both old clock and projected now, count paid timestamps strictly greater than time minus86400000 plus every held reservation. That sum must not exceed150. Exact equality at the left boundary is expired. Do not discard held reservations with age. All expiry is confined to this helper's demonstrably expired paid entries; legacy/unknown quest fields are outside its input and must remain preserved by the eventual caller.

Expose reserve(state,id,gold,now), complete(state,id,token,now), cancel(state,id,token,now) and inspect(state,now). Return {ok:false,why} for refusal. Successful state-changing projections return a detached next record. reserve refuses an already held ID, a fourth open scene, insufficient shared allowance or exhausted serial, otherwise increments serial and returns the new token. complete requires the exact ID/token, removes the reservation and appends its original gold at now, returning that gold. cancel requires the exact ID/token and releases it without payout or completion cooldown. complete/cancel must not act on a newer reservation for the same ID; token is essential for delayed calls. inspect returns active paid/reserved/available gold and open count without a state write. A refuse path never advances clock or serial and no operation mutates its inputs.

The helper does not store personal quest cooldowns. The future controller owns those, original terms and objective proof, using the same CAS; checking only this accounting result cannot permit acceptance or payout. Existing legacy rewards are not retroactively charged. This first module needs only a bounded accounting list, not the unfinished complete quest-state schema.
