Issue1373: proposed Windows stopped-world durability protocol. SOURCE DESIGN DIRECTION ONLY. Three fresh review cycles and independent read-only CLI reviews are complete; final reviews found no remaining contradiction within this direction contract. No implementation or operational readiness is claimed.

The deployed game servers use Windows Server. Existing FileDatabase commits file bytes and uses write-through replacements, but its directory barrier is uncertified on Windows and SupportsDurableUpsert remains false. Preserve that declaration. Do not implement a Linux-only opt-in or relabel a non-durable observation as a durable drain.

Separate two explicit phases. A native CompleteSavesForShutdown(timeoutMs) would finish already accepted save work, including storage settlement, with a monotonic observed-failure fence. The17Oct reviewed core proposal is wiki/merchant-terminal-accepted-save-core.md: blanket live-form staging is withdrawn because restored or silent live state must not overwrite accepted snapshots. Producers explicitly stage newer state before cutoff; native draining does not manufacture writes. Fresh and independent plan reviews found NONE. Addon entry and Windows integration remain separate dependent work. Its typed result is only a writes-completed observation, with durability capability recorded separately. It is not a shutdown or migration certificate. No supported caller may return to gameplay after using it to request maintenance: a dedicated local maintenance caller records its process identity, exact engine/source/channel/world-path identity and a fresh request nonce, then exits synchronously without another event-loop turn. Invalid timeout, loading, prior/current error, pending callbacks, unsupported settlement, deadline or recursive/cross-thread use refuses. Current false durability cannot be silently accepted by a strict durable caller. Existing stricter DrainSaveStorage proposal is superseded only if this composite protocol passes review.

A separate elevated Windows offline wrapper, run only by Claude, must prevent task/watchdog restarts and other writers for the entire transaction. Match the writes-completed record to the exact process, creation time, requested nonce, engine binary hash, channel and canonical private world/ledger paths. Hold an actual process handle and require its signaled exit with the expected code; verify port ownership and prevent replacement processes. An absent port alone is never evidence. Require FileDatabase and local fixed-volume paths; refuse network/ZIP/Mongo/migration stores and unknown providers. Resolve every affected world, ledger, journal and receipt path through its real Windows volume identity, including mount points/junctions, and reject unexpected paths or changes. Do not infer a volume from a drive-letter string.

Before granting the durable-stopped phase, open each distinct affected local volume using CreateFileW with GENERIC_WRITE, OPEN_EXISTING and compatible sharing, call FlushFileBuffers, check every result, and close handles. Microsoft documents volume flush and the required administrative privilege. A failure, missing privilege or unsupported volume refuses before any initializer/cut. This is one offline barrier, not a volume flush for every runtime save. Keep producer exclusion in force. After that barrier, validate all saved rows and journal state strictly, reconcile legacy merchant transfers and compare expected source evidence, then make a complete private snapshot with manifest and content hashes before any migration. A native completion observation without this barrier cannot authorize a cut. Hardware/storage promises remain those of the documented flush API, not an invented guarantee against broken hardware.

Any offline initializer must also make its own transaction output durable on these volumes before emitting completion evidence. Its output is bound to old and new roster/data/plugin hashes, channel, world/ledger identities, snapshot hash and request nonce. Failed validation or write never enables admission. Unknown or malformed saved records are preserved and refused rather than discarded. Rollback uses the complete snapshot only while stopped and producer exclusion remains held. Restart with the new source is a separate Claude release step after successful evidence, matching client admission and current-head CI/build integration. No source lane runs any of these operations.

Required protocol details from design review, overriding any shorthand above:

1. Establish and durably publish a protected maintenance epoch before requesting completion. Every supported game startup/admission and watchdog path must honor it. Wrapper crash, reboot, timeout, uncertain evidence or partial migration leaves the epoch in force. Recovery reacquires writer exclusion and validates the persisted phase. Clear the epoch only after durable verified migration or durable verified rollback, never merely because the wrapper exits. Source implementation must enumerate these entry points; an unsupported launch path blocks activation.
2. Establish a monotonic native maintenance latch and explicit acceptance cutoff before snapshot enumeration. Account for every previously accepted queued/in-flight change. Exclude gameplay and background mutation producers; callbacks may finish accepted work but any new post-cutoff mutation must be detected and refuse completion. Do not silently discard accepted work or assume callback-only pumping is mutation-free. Shutdown handlers cannot mutate the world after successful completion. The exact cutoff/allowed-callback contract needs a separate bounded design before native implementation.
3. Acquire the process handle before requesting completion, generate an unpredictable wrapper nonce, and deliver it through authenticated local IPC or a precreated protected handle. Restrictive ACLs and retained handles define the trusted issuer/transport. Parse bounded exact-schema evidence and consume it exactly once. A copied nonce plus matching fields is not authentication. Final migration completion binds the actual post-migration world/ledger manifest hashes as well as input/source/plugin identities.
4. Resolve existing directories/files through retained Windows handles and record stable volume/file identities, using GetFinalPathNameByHandleW and checked volume discovery. GetVolumePathNameW alone neither proves existence nor prevents path replacement. Protect ancestors and reparse-point changes throughout the transaction. Include snapshot destinations and all future output/evidence parents in the volume set. Use GUID volume names without a trailing slash, noninheritable handles, GENERIC_WRITE, OPEN_EXISTING, and FILE_SHARE_READ | FILE_SHARE_WRITE. Check each open, flush and close; a refusal cannot emit the next phase.
5. Validate source read-only, create the complete private snapshot, verify every copied hash, flush all snapshot destination volumes, then publish and flush a protected snapshot-ready checkpoint before the first migration write. A flushed source does not make a later buffered snapshot durable. After migration, flush output volumes, publish and flush the protected completion checkpoint, then allow epoch clearance. Rollback validates the complete snapshot, restores while stopped/excluded, verifies restored hashes and crosses its own checked volume/checkpoint barrier before restart.
6. Epoch clearance additionally requires a durably published release/admission manifest pinning every supported startup path to the attested engine, plugins, gamemode, roster and data identities. A source merge, successful migration or queued future deployment is insufficient. Until Claude has performed and attested that separate release integration, the epoch remains closed. Rollback must durably pin the corresponding old identities before clearance. A watchdog must never start old source against migrated data after a crash.
7. Treat one-use observation consumption and phase advancement as the same durable transaction transition. Every checkpoint contains the epoch/request identity, strict sequence and previous checkpoint hash, exact input/output manifest hashes and consumed observation identity. Before the first mutation, publish and flush a mutation-authorized checkpoint that consumes the observation and binds the durable snapshot. Recovery never consumes that observation again or restarts arbitrary mutation: a verified mutation-authorized/incomplete state permits only manifest-driven completion or exact rollback while excluded. Use bounded strict parsing, checksums and recoverable publication with retained prior checkpoints; reject torn, missing, conflicting or out-of-order records. For each write/rename/flush interval, define whether recovery uses the last intact phase or refuses operator intervention. Do not assume a multi-sector checkpoint write is atomic. A detailed transition table and injected crash tests are required before implementation stands.
8. Rollback verifies exact private-world namespace equality, including required absences, not only hashes of files copied back. Inventory every migration-created row, journal, receipt and checkpoint under transaction ownership. Remove or quarantine only those exact owned additions while excluded; preserve unknown data and refuse instead of deleting it. Restore and verify every original manifest member, verify no transaction-created runtime member remains, then flush the restored namespace and publish/flush the rollback checkpoint before the old release manifest can permit restart. Interrupted rollback remains closed and resumable from its durable manifest.

Scope of the preservation guarantee: this protocol may authorize mutation only after successful native completion, verified exit, the initial checked volume barrier and a verified durable rollback snapshot. It then preserves every accepted save included in that boundary through migration or rollback. It does not newly guarantee recovery of queued or non-durable runtime work if the server crashes before the initial barrier; every backend remains false and no global crash-durability guarantee is added. Such an interrupted pre-barrier run emits no authorization, retains the maintenance epoch and requires explicit recovery instead of applying the NPC cut. If the requirement is unconditional preservation before that first barrier, a separate durable acceptance journal/runtime backend guarantee is necessary; this composite protocol alone cannot satisfy it.

The Windows volume-flush primitive is supported by the primary driver documentation: DispatchFlushBuffers connects FlushFileBuffers to the flush IRP, and FltFlushBuffers describes volume flushing of modified-file data and metadata plus synchronization with underlying storage. This supports the proposed offline barrier under the documented storage guarantees; it does not supply the omitted process, cutoff, snapshot or admission protocol.

Proof still needed before selecting this design: review the exact Windows path/volume, durable epoch, authenticated IPC, cutoff and service/watchdog exclusion implementations, validate stale/forged/one-use evidence rejection, and test crash recovery at every persisted phase. Unit fakes cannot certify actual Windows persistence; source tests prove refusal and sequencing, and Claude must record real barrier results during authorized maintenance. No privileged local volume flush is a test in this task. Implement native completion, offline barrier/evidence and initializer as separate bounded changes with fresh and automatic independent read-only reviews.
